## Difference between the Pre-MMR and Post-MMR phases

DocuSearch divides its pipeline into two sequential phases: **Pre-MMR retrieval and selection**, followed by **Post-MMR per-chunk evaluation** [1].

### 1. Pre-MMR: retrieve and select evidence

The **purpose** of the Pre-MMR phase is to find and prioritize potentially relevant evidence for the query. It first selects an answer template, extracts domain-specific BM25 keywords, and may detect a vendor namespace [1][2]. It then runs dense-vector search, BM25 retrieval, and knowledge-graph expansion in parallel [1][2].

The results are combined using weighted Reciprocal Rank Fusion, reranked with a cross-encoder, and finally filtered with Maximal Marginal Relevance (MMR), which considers both relevance and diversity [1][2]. The output is therefore an **ordered set of MMR-selected chunks**, denoted as the evidence set \(\mathcal{E}\), which is passed to the next phase [1][2].

### 2. Post-MMR: evaluate evidence and produce an answer

The **purpose** of the Post-MMR phase is to determine whether an individual selected chunk is sufficient and safe to use for answering the query. Each chunk is processed through context-need detection, sufficiency scoring against a threshold of \(\tau=7\), answer generation, and groundedness verification [1].

The system examines the MMR chunks sequentially. If a chunk needs more context, neighboring chunks can be fetched; answer generation is allowed only after the sufficiency check, and the generated answer must then pass groundedness verification [2]. The first chunk that passes all checks produces the final answer and terminates the pipeline [1][2].

If no individual MMR chunk passes these checks, DocuSearch falls back to merging all expanded contexts, generating a consolidated answer, and performing one final groundedness check [1][2].

### Comparison

| Aspect | Pre-MMR | Post-MMR |
|---|---|---|
| **Main purpose** | Retrieve, combine, rerank, and diversify candidate evidence [1][2] | Evaluate selected chunks and generate a grounded answer [1][2] |
| **Input** | User query \(q\) [1] | Ordered MMR-selected chunks [2] |
| **Main operations** | Vector search, BM25, KG expansion, RRF fusion, cross-encoder reranking, and MMR selection [1][2] | Context expansion when needed, sufficiency checking, answer generation, and groundedness verification [1][2] |
| **Output/effect** | An ordered evidence set for downstream evaluation [1][2] | A verified answer, either from the first passing chunk or from fallback merging [1][2] |

Thus, **Pre-MMR is primarily an evidence-retrieval and selection stage**, whereas **Post-MMR is an answer-validation and generation stage**. The paper’s naming also makes an important sequencing distinction: although the Pre-MMR phase contains the actual MMR operation at its end, the Post-MMR phase begins only after MMR has produced the ordered chunks [2].
